## 0. 一句话产品定义

一条竖着的中轴把屏幕劈成两半：**左边记「让我变好的事」，右边记「让我难受的事」**，按天分组、过去在上方、今天在底部（`reverseLayout = true`），往上翻看历史。
核心不是"记账式"的效率工具，而是**降低记录的心理成本**——所以配色刻意避开红/绿的对立语义，用低饱和的暖色。

三个不可让步的设计约束：

| 约束 | 为什么 | 在哪里落地 |
|---|---|---|
| 左右分栏必须共用**一条连续中轴** | 轴断了，"一天"这条时间线就断了，产品隐喻失效 | `TimelineRow.kt`：`Row(左侧 weight(1f) | 中轴 44dp | 右侧 weight(1f))` |
| 日期分组必须是**真实列表项**，不能用 `stickyHeader` | 吸顶浮层会盖住中轴；且它不参与 Paging 的 itemCount，翻页边界会丢组头 | `TimelinePagingSource.kt` 按天分页 + `DayHeaderRow` 作为普通 item |
| 数据库**只存相对路径**，不存字节流 | 一次导入几百个视频时，把 blob 塞进 SQLite 会让 DB 涨到 GB 级、且 VACUUM 卡死 | `RecordEntity.imagePaths: List<String>`（JSON 串），媒体实体落在 `media_files` 表 |

**有意不引入的依赖**：

- **Hilt / Koin**：依赖图只有 8 个对象、一条链（`db → media/settings → repo → services`）。Hilt 带来的 KSP 生成 + 编译时间 + "为什么注入不上"的排查成本，换不来收益。迁移点已预留在 `DaylineApp.kt` 的 `AppContainer`。
- **navigation-compose**：只有 4 个目的地，用 `sealed interface Screen` + `BackHandler` 的行为完全可预测，还少一层参数序列化。
- **Zip4j**：`java.util.zip` 够用，且能在 JVM 单测里跑真 zip 往返。
- **WorkManager**：回收站过期清理在 `Application.onCreate` 里起一个协程跑一次即可，不值得引入后台调度框架。若将来要做"每日备份提醒"，再从 WorkManager 起步。

## 2. 数据层设计（Room）

### 2.1 表结构

**`records`（记录主表）**

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | UUID 字符串。用 UUID 而不是自增 int，是为了多设备合并时 id 不撞车 |
| `content` | TEXT | 正文 |
| `side` | TEXT | `beneficial` / `bad` |
| `recordDate` | TEXT | **`yyyy-MM-dd` 字符串**，天粒度 |
| `createdAt` / `updatedAt` | INTEGER | epoch millis |
| `isDeleted` / `deletedAt` | INTEGER / INTEGER? | 软删除（回收站） |
| `imagePaths` / `videoPaths` / `videoCoverPaths` | TEXT | JSON 数组，存**相对 `filesDir` 的路径** |
| `contentFingerprint` | TEXT? | 内容级去重指纹；删除时置 NULL |

索引：`recordDate`（分页排序）、`isDeleted`（回收站查询）、`updatedAt`（合并比较）、`contentFingerprint`（去重查找）。

**为什么 `recordDate` 用字符串而不是时间戳**：用户关心的「哪一天」是**本地日历日**。用毫秒时间戳存，跨时区/夏令时会把同一天切成两天，日期吸顶头随之重复出现。字符串 `yyyy-MM-dd` 天然是字典序 = 时间序，`DISTINCT + ORDER BY DESC` 直接可用，无需函数索引。

**`tags`**：`id` PK、`name` 唯一索引、`createdAt`。
**`record_tag`**：复合主键 `(recordId, tagId)`，双向 CASCADE 外键，`tagId` 单独索引。
**`media_files`**：`sha256` PK、`relativePath` 唯一索引、`kind`、`sizeBytes`。

### 2.2 类型转换

`Converters` 把 `List<String>` ↔ JSON 串。关键细节：**解析失败返回空列表而不是抛异常**。

```kotlin
fun toStringList(value: String?): List<String> {
    if (value.isNullOrBlank()) return emptyList()
    return runCatching { json.decodeFromString(listSerializer, value) }
        .getOrDefault(emptyList())
}
```

理由：坏数据（比如手改 DB、或旧版本字段格式变更）不该让**整条记录读不出来**。宁可丢媒体路径，也要保住正文。

### 2.3 DAO 设计要点

分页走**两条 SQL**，而不是一条大 JOIN：

```sql
-- ① 取一页日期
SELECT DISTINCT recordDate FROM records
WHERE isDeleted = 0 ORDER BY recordDate DESC LIMIT :limit OFFSET :offset

-- ② 取这些日期下的全部记录（含标签，@Transaction）
SELECT * FROM records
WHERE isDeleted = 0 AND recordDate IN (:dates)
ORDER BY recordDate DESC, createdAt ASC, id ASC
```

第 ② 条用 `IN (:dates)` + `ORDER BY createdAt ASC`；配合 `TimelineScreen` 的 `reverseLayout = true`，`TimelinePagingSource` 在组装每页数据时按天内倒序 + 日期头置后，渲染后自上而下为**日期头 → 当天记录按时间先后**，且**今天在最底部、过去在上方**。

`RecordWithTags` 用 `@Relation + Junction` 一次查出标签，避免 N+1。

## 3. 分页与预加载（Paging 3）

### 3.1 按「天」分页，不按「记录」分页

这是本方案最重要的一个决策。

如果按记录分页（`LIMIT/OFFSET` 落在 records 上），**跨页边界上的日期组头无法稳定生成**：第 1 页的最后一条是 11-14 号，第 2 页的第一条也是 11-14 号，两页各自都会插一个"11月14日"的头，滚动时就会看到重复日期。

按天分页则天然没有这个问题：一个 `LoadResult.Page` 的边界永远落在"天"与"天"之间。

```kotlin
val dates = dao.pageDates(limit = daysPerPage, offset = page * daysPerPage)
val records = dao.recordsForDates(dates)
val byDate = records.groupBy { it.record.recordDate }
val items = ArrayList<TimelineItem>()
for (date in dates) {
    items += TimelineItem.DayHeader(date)          // 组头
    byDate[date]?.forEach { items += TimelineItem.Entry(it) }
}
```

`DEFAULT_DAYS_PER_PAGE = 7`（一页一周）。取值考量：记录密度低的用户（一天 1-2 条）一页只有 7-14 条，翻页太频繁；密度高的用户（一天 10 条）一页 70 条，一次性组装 70 个 item 也就几毫秒。7 是两头都能接受的折中。

### 3.2 预加载的两条路径（缺一不可）

```kotlin
PagingConfig(
    pageSize = 7,
    prefetchDistance = 2 * 7,   // 路径 1：数据层，距末尾 14 条时自动请求
    enablePlaceholders = false, // 路径 2 的前提：无占位符，itemCount 才是真实条数
    initialLoadSize = 7
)
```

```kotlin
// 路径 2：UI 侧触底提前量
internal fun computeShouldLoadMore(state: LazyListState, thresholdPx: Float): Boolean {
    val layout = state.layoutInfo
    if (layout.totalItemsCount == 0) return false
    val last = layout.visibleItemsInfo.lastOrNull() ?: return true
    val pxLeft = layout.viewportEndOffset - (last.offset + last.size)
    val indexLeft = layout.totalItemsCount - 1 - last.index
    return indexLeft <= 2 || pxLeft <= thresholdPx   // 600dp
}

LaunchedEffect(items, shouldLoadMore) {
    if (!shouldLoadMore) return@LaunchedEffect
    val state = items.loadState
    if (state.append is LoadState.Loading || state.append is LoadState.Error) return@LaunchedEffect
    if (items.itemCount > 0) items[items.itemCount - 1]   // ← 真正的触发动作
}
```

**这里有个坑必须写清楚**：`items.loadState.append = LoadState.Loading` 这种写法**不会触发加载**——`loadState` 是状态快照，赋值只是改了本地那份数据。真正的触发是**访问一个尚未加载的位置**（`items[last]`），由 Paging 内部去判断"这个位置没有数据 → append"。

为什么两条都要：
- 用户慢速滚动时，路径 1 就够；
- 用户一把甩到底（fling）时，`prefetchDistance` 常常来不及响应（一次 fling 能滚过几十条），这时路径 2 的 600dp 提前量兜住。

还有第三种边界：**首屏不满一屏**（比如总共只有 2 条记录）。此时 `shouldLoadMore` 可能一次都不为 true。所以补一个跟着布局变化的 `snapshotFlow`，当"可见项数 == 总项数"且 `!endOfPaginationReached` 时再补一次 `items[itemCount - 1]`。

### 3.3 `cachedIn(viewModelScope)`

```kotlin
val timeline: Flow<PagingData<TimelineItem>> = repo.timeline.cachedIn(viewModelScope)
```

不加 `cachedIn` 的后果：每次重组（比如旋转屏幕、切到设置页再回来）都会重建 Pager，列表**闪回第一页**并重新请求。这是 Paging 3 最常见的线上问题。

## 4. UI 层（Compose）

### 4.1 双栏时间轴的行结构

```
┌──────────────┬──────┬──────────────┐
│  卡片(weight1)│ 中轴 │   空(weight1) │   ← 有益
├──────────────┼──────┼──────────────┤
│   空(weight1) │ 中轴 │ 卡片(weight1) │   ← 糟糕
└──────────────┴──────┴──────────────┘
                    44dp
```

```kotlin
Row(Modifier.fillMaxWidth().height(IntrinsicSize.Min)) {
    Box(Modifier.weight(1f).fillMaxHeight(), contentAlignment = Alignment.TopEnd) { if (isLeft) RecordCard(...) }
    TimelineAxis(Modifier.width(44.dp).fillMaxHeight(), dotColor = colors.accent)
    Box(Modifier.weight(1f).fillMaxHeight(), contentAlignment = Alignment.TopStart) { if (!isLeft) RecordCard(...) }
}
```

两个技术要点：

1. **`weight(1f)` 而不是 ConstraintLayout**：两个等权槽位会把 44dp 中轴**精确居中**，且卡片宽度自适应屏幕，横竖屏都不用改一行。ConstraintLayout 在这里只是多一层依赖。
2. **`height(IntrinsicSize.Min)` + `fillMaxHeight()`**：让中轴竖线的长度**恰好等于卡片高度**。如果不这么做，竖线要么按固定高度画（和卡片高度不匹配，出现"线比卡片长一截"的割裂感），要么根本画不满行高。

中轴的竖线和圆点用 `drawBehind` 画，不额外套 `Canvas` 组件。理由：一屏 20+ 行，每行少一个布局节点，滚动掉帧会少一截。

### 4.2 日期头

`DayHeaderRow` 是**普通列表项**，高度 64dp，由「左半段横线 + 日期胶囊 + 右半段横线」组成，横线用 `outlineVariant`，与中轴同色系，视觉上"轴穿过日期"。

文案规则在 `Dates.kt`：

| 偏移 | 主标题 | 副标题示例 |
|---|---|---|
| 0 天 | 今天 | 11月14日 · 周六 |
| 1 天 | 昨天 | 11月13日 · 周五 |
| 2 天 | 前天 | 11月12日 · 周四 |
| ≥3 天 | 11月11日 | 11月11日 · 周三 |
| 跨年 | 2025年12月31日 | 2025年12月31日 · 周三 |

「今天」也带具体日期，是为了让用户不必心算"今天几号"。

### 4.3 治愈暖色系

| 语义 | 浅色值 | 说明 |
|---|---|---|
| 背景 | `#FDF8F3` 奶油白 | 不用纯白，降低长时间盯屏的刺激 |
| 正文 | `#4A3F35` 暖棕 | 对背景对比度 ≈ 9.6:1 |
| 次要 | `#8A7A68` | ≈ 4.6:1，满足 WCAG AA 正文 4.5:1 |
| 左栏容器 | `#F2F6E6` 奶油绿 | |
| 左栏强调 | `#6F8F4E` 橄榄绿 | 不用鲜艳绿，避免"打卡成功"的绩效感 |
| 右栏容器 | `#F6EBE4` 灰粉 | |
| 右栏强调 | `#B07A5E` 陶土橙 | **不用红**——记录负面情绪时红色会放大羞耻感 |
| 危险（删除确认） | `#9C5B4B` | 压饱和的红棕，够警示但不刺眼 |

深色模式**不是简单反色**，而是重新挑了一组「深咖底 `#201A16` + 低饱和暖色块」。原因：暖色在纯黑上会发荧光，"治愈暖"会变成"脏橘"。底色用 `#201A16` 而不是 `#000000`，两侧卡片靠**边框**而不是亮度差区分。

字号体系比 Material 默认小一档（正文 15sp、卡片标题 16sp、日期头 19sp）：时间轴卡片本身不大，字号大了换行难看。

### 4.4 交互动效与可达性

- **FAB**「记一笔」→ 直接进入编辑页（默认选中「有益」，可在编辑页顶部切换「有益 / 糟糕」）。
- 卡片点击 → 编辑页；媒体缩略图单独可点 → 系统看图/播放器（`FileProvider` + `ACTION_VIEW`）。
- 删除：编辑页垃圾桶 → 二次确认「移到回收站」→ Snackbar 可撤销。
- 所有可点区域 ≥ 48dp（`IconButton` 默认 48dp；自定义的 `RemoveBadge` 视觉 24dp，但 `IconButton` 撑到 24dp 时用 `size(24.dp)` 是唯一例外——它叠在缩略图角上，必须小；点击热区由外层卡片兜底）。

## 5. 媒体处理

### 5.1 私有目录与内容寻址

```
filesDir/
  media/images/<sha前2位>/<sha256>.jpg
  media/videos/<sha前2位>/<sha256>.mp4
  media/covers/<sha前2位>/<sha256>.jpg
```

**文件名用 sha256，不用 UUID**。收益：

- 同一张图被选中两次（或导出再导入）**天然只存一份**，去重不需要额外逻辑；
- 导入时"按哈希复核"就等价于"按文件名复核"；
- 分两级目录（前 2 位）避免单目录几万个文件导致 `readdir` 变慢。

代价：扩展名只能靠 mime 猜，所以统一转成 `.jpg` / `.mp4` 固定后缀。对个人记录 App 来说，这个代价可以接受。

### 5.2 导入（从系统相册）

```kotlin
// MediaStore.importFromUri
cacheDir/import-<uuid>  ← contentResolver.openInputStream 复制
sha256Of(tmp)           ← 边读边算，不额外遍历一次
target = filesDir/media/images/<xx>/<sha>.jpg
if (!target.isFile) copy else 复用
```

先落到 `cacheDir` 再算哈希的原因是：内容寻址要求**先知道哈希才能定文件名**，而 sha256 必须读完整个文件。用临时文件避免把整张图读进内存（一张 4000×3000 的 JPEG 解码后约 36MB，绝不能整块进堆）。

### 5.3 视频封面

`MediaMetadataRetriever.getFrameAtTime(0, OPTION_CLOSEST_SYNC)` 取首帧 → 缩放到最长边 720px → JPEG q82 → 存 `media/covers/<sha>.jpg`。

- `OPTION_CLOSEST_SYNC` 而不是 `OPTION_CLOSEST`：后者要为找精确帧解码更多 GOP，慢一个数量级，而封面帧差一帧完全无所谓。
- 已存在同名封面直接复用（`isFile && length > 0`），不重复解码。
- 失败返回 `null`，UI 显示占位图标；点一下仍能播。**不能因为封面提取失败就丢掉视频**。

### 5.4 Coil 按尺寸解码

```kotlin
AsyncImage(
    model = ImageRequest.Builder(context)
        .data(file)
        .size(300)                                  // 只解码到 300px
        .memoryCacheKey("thumb:$relativePath@300")  // 按尺寸分桶缓存
        .crossfade(true)
        .build(),
    contentScale = ContentScale.Crop
)
```

不显式给 `size` 的话，Coil 会按**原图尺寸**解码再缩小——一张 4000×3000 的照片峰值内存几十 MB，列表里滚动几十张就 OOM。`memoryCacheKey` 带尺寸，是为了同一张图在列表（300px）和编辑页（88dp 缩略）两种场景下各自缓存，不会互相踢掉。

列表不自动播放视频：只显示封面 + 半透明黑底播放角标。这是产品决策也是性能决策——一屏 10 个视频同时解码，中端机会直接卡死。

## 6. 设置（DataStore）

5 个配置项：`beneficialLabel`、`badLabel`、`beneficialCustom`、`badCustom`、`trashRetentionDays`。

`beneficialCustom` / `badCustom` 这两个"用户是否自定义过"的布尔位，是为了**导入合并不覆盖用户的命名**：只有当本地没自定义过、且导入方自定义过时，才采用导入值。

```kotlin
suspend fun mergeFromImport(imported: SettingsSnapshot) {
    val local = snapshot()
    context.dataStore.edit { p ->
        if (!local.beneficialCustom && imported.beneficialCustom) { ... }
        if (!local.badCustom && imported.badCustom) { ... }
    }
}
```

设置页**不做输入即保存**：左右分类名用本地 `rememberSaveable` 暂存，点「保存」或失焦才写 DataStore，避免每敲一个字写一次文件。

`trashRetentionDays` 用 `stringPreferencesKey` 存而不是 `intPreferencesKey`——DataStore Preferences 没有 int key，只有 `intPreferencesKey`（有，但 `SettingsRepository` 里统一用 string 便于容错：`toIntOrNull() ?: 默认值`，坏值不会崩）。

## 7. 导入导出

### 7.1 文件名规则

`records_yyyy-MM-dd.zip`，日期取**导出当天的本地日期**。
重名：`records_2026-11-14.zip` → `_1.zip` → `_2.zip` … → `_99.zip` → 超过 99 次退回 `_HHmmss`。

为什么优先序号而不是时间戳：用户一眼能看出"这是今天第几次导出"。序号上限 99 是为了避免文件名无限变长。

### 7.2 包内结构

```
records_2026-11-14.zip
 ├─ records.json                    # 全量记录（含已删除）+ 标签 + 设置
 ├─ media/images/ab/abcd….jpg
 ├─ media/videos/ab/abcd….mp4
 └─ media/covers/ab/abcd….jpg
```

**zip 内路径 == 应用内相对路径**。这样 `records.json` 里的 `imagePaths` 拿去直接用，导入方零映射。

压缩策略：`records.json` 用 DEFLATE；`jpg/png/webp/mp4/heic` 用 STORED。理由：这些格式已经压过，再 deflate 一遍只浪费 CPU（导入导出都在主线程之外，但大视频能省几十秒）。

`records.json` 放**第一项**，因为部分解压工具按顺序流式读。

### 7.3 导出是否包含已删除记录

**包含**。理由：不包含的话，"换机后回收站空了"和"我删掉的东西在朋友设备上又活过来"两种解释都很别扭。正确做法是导出 `isDeleted + updatedAt`，让合并算法按时间说话。

### 7.4 合并规则（`MergeEngine.decide`，纯函数）

按优先级判：

| 条件 | 决策 | 理由 |
|---|---|---|
| 本地无该 id，且 `isDeleted = false`，内容指纹未出现过 | `INSERT` | 新记录 |
| 本地无该 id，且 `isDeleted = true` | `INSERT` | 已删除记录**只按 id 合并**，不参与内容去重 |
| 本地有该 id，`导入.updatedAt > 本地.updatedAt` | `UPDATE` | 覆盖（含 `isDeleted` 状态）|
| 本地有该 id，`导入.updatedAt <= 本地.updatedAt` | `SKIP_OLDER` | 不能用旧数据盖掉新编辑 |
| 不同 id，但内容指纹已存在于本地或本批次 | `SKIP_DUPLICATE` | 内容级去重 |

**最容易写错的一条**：已删除记录**不能**参与内容去重。否则会出现："我在 A 机删了这条" + "B 机还有同内容的未删除副本" → 被当成重复跳过 → 删除状态丢失，或者反过来把用户的删除操作"复活"。

### 7.5 内容指纹

```
sha256( content.trim().空白归一 + \x01 + side + \x01 + recordDate
        + \x01 + 排序后标签 + \x01 + 排序后媒体sha256 )
```

三个刻意的归一化：

1. **空白归一**（`Regex("\\s+")` → 单空格）+"今天跑了步" vs "今天 跑了 步" 视为同一条。
2. **标签排序**：拖动标签顺序不该让记录"变成新的"。
3. **媒体 sha 排序**：图片拖动排序同理。

**不**参与指纹的：`imagePaths` 的**顺序**、`createdAt`。前者理由同上；后者是导出导入往返时毫秒级时间戳可能变，但"是不是同一条内容"与创建时刻无关。

### 7.6 zip-slip 防护（双保险）

第一道：`safeEntryName`
```
1. 反斜杠 → 正斜杠（Windows 打的包可能带 \）
2. 拒绝绝对路径 /^\/.*/
3. 拒绝盘符 /^[A-Za-z]:/
4. 拒绝 ".." 段、空段（"a//b"）、控制字符
5. 开头的 "./" 允许（很多打包工具这样写），只跳过，不当非法
```

第二道：`resolveInside`
```
target = File(rootCanonical, safeName).canonicalFile
assert target == root || target.path.startsWith(root.path + separator)
```
规范化后**再比一次**，即使第一道有漏洞也逃不出去。

这是整个导入流程里唯一"宁可失败也不能放行"的地方。历史上有大量 App 栽在 `../../` 上——攻击者构造一个恶意 zip，解压时覆盖 App 私有目录外的文件。

### 7.7 事务边界

```
① 解压全部媒体到 cacheDir/import-<uuid>/   （事务外）
② 逐个小文件: sha256 → adopt 到 filesDir    （事务外）
③ 合并决策（纯函数，不写库）
④ db.withTransaction { 标签 + 记录 + 关联 }  （单事务）
⑤ settings.mergeFromImport                  （事务外）
finally: 删 cacheDir/import-<uuid>/
```

**为什么媒体先落盘、数据库后写**：反过来（先入库再落盘）如果落盘失败，数据库会指向不存在的文件，用户看到一堆破图。而先落盘后入库即使③④回滚，最坏只是多几个没人引用的文件，由 `gcMedia` 兜底清理——**"多占点空间"是可以接受的失败模式，"数据损坏"不是**。

`settings.mergeFromImport` 放在事务外，因为 DataStore 有自己的写入机制（内部是文件的原子替换），不能参与 Room 事务。

### 7.8 导入报告

不用英文枚举，直接给中文一句话：

> 导入完成：新增 12 条，更新 3 条，去重跳过 5 条，本地较新跳过 2 条，恢复已删除 1 条，媒体 34 个；2 个文件损坏已跳过

用户要的是"我这次导入了什么"，不是 enum。

## 8. 状态管理与导航

### 8.1 单 Activity + sealed Screen

```kotlin
sealed interface Screen {
    data object Timeline : Screen
    data object Trash : Screen
    data object Settings : Screen
}
```

编辑页不是 `Screen` 的一个分支，而是**覆盖层**（`editor != null` 时全屏盖在上面）。原因：编辑页要能从时间轴、回收站、设置页任意位置唤起，做成路由会让返回栈出现"设置 → 编辑 → 返回 → 设置"还是"→ 时间轴"的歧义。

`BackHandler` 的优先级：`detail` > `editor` > `screen`。

### 8.2 单 ViewModel 的取舍

`DaylineViewModel` 是全应用唯一 VM。这不是偷懒：

- 时间轴、编辑页、回收站、设置共享同一个 `RecordRepository` 和 `SettingsRepository`；
- 拆成 4 个 VM 各自持有 Paging 流，会导致"编辑页保存后时间轴不刷新"这类问题**更难发现**；
- 页面数 < 10 时，单 VM + sealed 路由更好排查。

将来的拆分边界是 **Repository**，不是页面。

### 8.3 状态流的三种形态

| 形态 | 用途 | 例子 |
|---|---|---|
| `StateFlow<T>`（`stateIn`） | 有初始值、跨页面共享 | `settings: StateFlow<SettingsState>` |
| `Flow<PagingData<T>>`（`cachedIn`） | 分页数据 | `timeline` |
| `MutableStateFlow<T?>` + `consume` | 一次性事件（消息、导出结果） | `message`、`exportFile` |

`settings` 用 `stateIn(viewModelScope, WhileSubscribed(5_000), SettingsState())`，而不是手写 `MutableStateFlow` + `collect`——手写版本没有初始值语义，首帧会闪一下"默认名称"。

一次性事件必须在消费后置 null（`consumeMessage()`），否则旋转屏幕后会重放 Snackbar。

## 9. 性能与内存

| 风险点 | 措施 | 量化预期 |
|---|---|---|
| 图片 OOM | `ImageRequest.size(300)` 强制按显示尺寸解码 | 单图峰值从 ~36MB（4000×3000 ARGB）降到 ~0.36MB |
| 列表滚动掉帧 | 中轴用 `drawBehind` 而非 `Canvas` 节点；`DayHeader`/`Row` 均为普通 item | 一屏 20 行的节点数减少约 20 个 |
| 分页闪回第一页 | `cachedIn(viewModelScope)` | 消除重组时的重复加载 |
| 大文件导入 OOM | `copyTo(buffer=64KB)` 流式；sha256 边读边算；不 `readBytes()` 整个媒体 | 峰值内存与文件大小无关 |
| zip 写入卡顿 | `Dispatchers.IO` + 64KB buffer；媒体用 STORED | 导出 100 个媒体时不额外做一次 deflate |
| 数据库膨胀 | 媒体只存相对路径；`media_files` 只在删除时清 | DB 大小与媒体总量无关，通常 < 1MB |
| 封面重复解码 | `ensureCover` 前置 `isFile && length > 0` 判断 | 同视频二次进入列表 0 解码 |
| 无效媒体堆积 | `gcMedia` 在 purge/purgeAll/过期清理后扫引用 | 只删"没有任何记录引用"的文件 |

`PagingConfig.enablePlaceholders = false` 也是一个性能/正确性权衡：占位符能让滚动条长度稳定，但会让 `itemCount` 返回一个"预估总数"，而我们的 `computeShouldLoadMore` 依赖真实条数。个人记录 App 不需要精确滚动条，选 `false`。

2. **`ZipArchive.write` 对 STORED 条目读两遍**（先算 CRC 再拷贝）：1 GB 视频 = 2 GB 读 IO。
3. **DAO / Compose instrumentation 测试未写**：`pageDates` 的 `OFFSET` 分页在超大数据量下是线性扫描，单用户超过约 5000 天应改 keyset 分页。
